Preferred name: EGP
Role: Retired Software Developer

General collaboration
- Prefer low-context pair-programming sessions.
- Prefer concise checkpoints and summaries to keep chat context small.
- For project resume work, prefer a compact bootstrap package: state capsule, checkpoint, bootstrap prompt, and current task.
- Treat newly pasted files, errors, and test output as the current source of truth over older chat context.
- Discard obsolete prior versions once newer ones are provided.

Grounding and rigor
- Do not speculate about implementation details.
- If implementation details may have drifted, ask for a resync with the current code before proposing fixes.
- Prioritize mathematical correctness first, then testability, then design-for-test.

File organization and code structure
- Prefer fewer medium-sized cohesive files over many tiny files.
- Prefer methods around 30–40 lines so they fit on one screen.
- Break longer methods into smaller helpers for readability, testability, and safer refactoring.
- Split files over about 600 lines into smaller cohesive files; avoid tiny single-function files.

Testing
- Tests expected to run longer than about 1 minute should be bounded or redesigned to run quickly.
- For goCF, prefer test-first TDD in two phases:
  1. Make tests fail first; production stubs are allowed and expected failures may be asserted.
  2. Then implement production until green.
- Include visibility hooks and pre/post-condition checks where appropriate for design for test.

File edit style
- If a file is small, prefer a full replacement file.
- If a file is larger, prefer complete replacement functions rather than partial edits.
- Provide landmarks when replacing blocks of code.
- Prefer append-only changes where practical.
- Appending to the end of an existing file is even better when practical and coherent.
- When given code to append, omit filename/version comments.
- Include filename/version comments only for complete file replacements.
- It is okay to retain the most recently supplied version of a file as the source of truth until a replacement is provided.

Output and formatting
- When providing the contents of a markdown file such as MasterPlan.md, wrap the entire file in a text block for easy copy/paste.
- Shell commands intended for execution in zsh should be shown in text blocks.
- Default shell: zsh.

Go-specific conventions
- Provide Go code in go fenced blocks.
- For complete file replacements, include filename and version comment on the first and last line of each file.
- Version numbers start at v1 and increment when a file is revised.

Commit workflow
- When the user says "green", provide an appropriate git commit message for the most recent changes.
- The commit message should be in a text block, with a label outside the block.
- Also provide a commit message when green is expected and it is helpful to provide the message earlier.
- When providing a commit message, summarize all substantive work completed since the last time the user said "committed", not just the most recent fix or cleanup.
- If a commit message was provided in advance and tests are green, the user may reply "committed" instead of "green".

- For goCF collaboration, prefer full-file replacements for small files, full function replacements for larger files, and append new tests to the end of a file when possible.
